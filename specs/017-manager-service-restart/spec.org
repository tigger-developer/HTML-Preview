* Synopsis
:PROPERTIES:
:CUSTOM_ID: summary
:END:

** Outcome

- =make service-restart= *restarts the registered user service* through launchd
  on macOS or systemd on Linux.

** Before

- The target expressed stop and start as *independent Make prerequisites*, so
  parallel Make could schedule them concurrently.
- Linux inherited a *macOS-only activation path* instead of systemd lifecycle
  control.

** After

- The native manager *completes stop before start*.
- The target *does not launch the preview server directly* or replace a service
  definition.

** Changes

- The Go build tool owns one portable restart action selected by operating
  system.

** Unchanged

- Service installation, registration, configuration, logs and rendering
  behaviour *remain unchanged*.

** Edge cases
:PROPERTIES:
:CUSTOM_ID: synopsis-edge-cases
:END:

- A manager failure *stops the sequence and remains visible*; unsupported
  platforms are rejected.

** Decisions

- Use the existing stable launchd label and systemd unit name with *separate
  manager arguments and a bounded command deadline*.

** Next step

- Retrospective definition review, native user validation and operator closure.

* Context
:PROPERTIES:
:CUSTOM_ID: context
:END:

** Problem

The restart target does not own an ordered service-manager lifecycle and cannot
provide the same interface on macOS and Linux.

** Outcome

An invocation restarts the existing registered user service through the native
manager without creating an unmanaged background server.

** Scope

*** In scope

- =make service-restart=, build-tool dispatch, launchd and systemd user-service
  commands, manager errors, regression evidence and operational documentation.

*** Out of scope

- Installing or replacing service definitions, enabling Linux services,
  foreground service mode, Homebrew service control and Windows.

*** Unchanged

- Existing =make service= and =make service-stop= launchd installation and
  replacement behaviour remains intact.

** Constraints and dependencies
:PROPERTIES:
:CUSTOM_ID: constraints-and-dependencies
:END:

- The platform service must already be installed and registered.
- Manager commands receive literal argument vectors, preserve the inherited
  environment and complete within 30 seconds.

** Decisions

- macOS uses =launchctl stop= followed by =launchctl start= for
  =gui/<uid>/org.htmlpreview.agent=.
- Linux uses =systemctl --user stop= followed by =systemctl --user start= for
  =htmlpreview.service=.

** Unresolved blockers

- None for implementation and automated review. Native manager validation
  requires an installed user service.

* Solution Design
:PROPERTIES:
:CUSTOM_ID: solution-design
:END:

** Architecture context

- Relevant components :: Make exposes the operator command; the Go build tool
  owns bounded native process execution; launchd or systemd owns service state.
- Ownership boundary :: The project selects its stable user-service identifier;
  the native manager owns service installation state and lifecycle results.
- Existing pattern :: Reuse the build tool's explicit argument execution and
  the launchd label already owned by service replacement.

** High-level design

- Shared operation :: One function selects literal stop and start argument
  vectors, then executes them sequentially through one manager runner.
- Variation :: Darwin selects launchctl and the registered label; Linux selects
  systemctl user mode and the installed unit.
- Flow :: Make invokes the build-tool task; the task waits for stop; successful
  stop permits start; the final manager result becomes the command result.
- Failure behaviour :: Each manager call has a 30-second deadline. Stop or start
  output is retained in a contextual error; no retry or detached fallback occurs.
- Simplicity :: No new dependency, daemon, configuration, shell command string
  or replacement transaction is introduced.

** Design decisions and verification

*** Manager lifecycle is the only restart path

- Decision :: The target performs only native manager stop and start operations.
- Verification :: [[#rt-017-1][RT017.1 - Native manager restart sequence]]
  captures every external call and failure transition.

** Routine details left to implementation

- Internal function names and error wording may follow established build-tool
  conventions while retaining the defined context.

** Architecture impact

*** Security impact

- Threat boundary :: The existing per-user manager boundary is unchanged.
- Data and secrets :: No document data, configuration contents or service logs
  are read or emitted.
- Access :: No privilege escalation, system service or service enablement is
  added.
- Conclusion :: Existing least-privilege ownership remains sufficient.

*** Other relevant qualities

- Portability :: One operator target now has defined macOS and Linux behaviour.
- Reliability :: Ordered execution removes concurrent prerequisite scheduling.
