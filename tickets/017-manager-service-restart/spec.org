* Synopsis
:PROPERTIES:
:CUSTOM_ID: summary
:END:

** Outcome

- =make service=, =make service-stop= and =make service-restart= *control the
  registered user service* through launchd on macOS or systemd on Linux.

** Before

- Restart expressed stop and start as *independent Make prerequisites*, so
  parallel Make could schedule them concurrently.
- Source-checkout start and stop were *macOS-only*, while restart alone selected
  systemd on Linux.

** After

- All three targets *use the native user manager* on macOS and Linux.
- Restart *completes stop before start* without regenerating the definition.
- No lifecycle target *launches the preview server directly*.

** Changes

- The Go build tool owns one portable lifecycle route selected by operating
  system; Linux activation atomically installs the checkout's user unit.

** Unchanged

- macOS LaunchAgent replacement, explicit installation, Homebrew control,
  configuration, logs and rendering behaviour *remain unchanged*.

** Edge cases
:PROPERTIES:
:CUSTOM_ID: synopsis-edge-cases
:END:

- A manager or configuration failure *stops the sequence and remains visible*;
  unsupported platforms are rejected.

** Decisions

- Reuse the existing stable launchd label and systemd unit name with *literal
  manager arguments, atomic definition replacement and a bounded deadline*.

** Next step

- Delivery-code review, retrospective definition review, native user validation
  and operator closure.

* Context
:PROPERTIES:
:CUSTOM_ID: context
:END:

** Problem

The source-checkout service targets do not provide one coherent native-manager
lifecycle across macOS and Linux.

** Outcome

Start, stop and restart operate on the platform's registered user service
without creating an unmanaged background server.

** Scope

*** In scope

- =make service=, =make service-stop= and =make service-restart=; build-tool
  dispatch; launchd and systemd user-service definitions and commands; manager
  errors; regression evidence and operational documentation.

*** Out of scope

- Root or system services, foreground service mode, Homebrew service control,
  automatic systemd enablement outside explicit =make service=, and Windows.

*** Unchanged

- Existing launchd installation and rollback behaviour remains intact. Explicit
  package installation still installs inactive service examples only.

** Authority and starting point

- Project profile :: [[file:../../.sdlc/project.yaml][=.sdlc/project.yaml=]]
- Product authority :: [[file:../../docs/SERVICE.md][Service guide]]
- Architecture authority :: [[file:../../docs/ARCHITECTURE.md][Architecture]]
- Historical requirement :: [[file:../012-install-service-replacement/spec.org][W012 - Service replacement]]
- Current implementation :: [[file:../../Makefile][Make interface]] and
  [[file:../../internal/buildtool/main.go][build-tool dispatch]]
- Emergency expansion :: The 2 October 2026 emergency correction supersedes
  W017's restart-only and Linux-manual boundaries for these three Make targets.

** Constraints and dependencies
:PROPERTIES:
:CUSTOM_ID: constraints-and-dependencies
:END:

- Restart and stop require an existing registered service. Start creates or
  replaces the source-checkout definition before manager activation.
- Manager commands receive literal argument vectors, preserve the inherited
  environment and complete within 30 seconds.

** Decisions

- macOS uses =launchctl stop= followed by =launchctl start= for
  =gui/<uid>/org.htmlpreview.agent=.
- Linux uses =systemctl --user stop= followed by =systemctl --user start= for
  =htmlpreview.service=.
- Linux start atomically writes =~/.config/systemd/user/htmlpreview.service=,
  then invokes =daemon-reload=, =enable= and =restart= in order so a changed
  checkout takes effect even when the unit is already running.

** Unresolved blockers

- None for implementation and automated review. Native manager validation
  requires platform user-service operation.

:PROPERTIES:
:CUSTOM_ID: ac-017-3
:END:

- Criterion :: On Linux, =make service= *atomically replaces the user unit*,
  preserves any symlink target, enables it and restarts it so the current
  checkout becomes active. Stop retains the unit and enabled state.

* Solution Design
:PROPERTIES:
:CUSTOM_ID: solution-design
:END:

** Architecture context

- Relevant components :: Make exposes the operator commands; the Go build tool
  owns definition generation and bounded native process execution; launchd or
  systemd owns service state.
- Ownership boundary :: The project selects its stable user-service identifier;
  the native manager owns service installation state and lifecycle results.
- Existing pattern :: Reuse the build tool's explicit argument execution,
  service template renderer and launchd replacement boundary.

** High-level design

- Shared operation :: One platform dispatcher routes start and stop to the
  existing Darwin boundary or the Linux user-service boundary. Restart selects
  literal stop and start arguments through the shared manager runner.
- Variation :: Darwin retains plist replacement, bootout and bootstrap. Linux
  renders the existing unit template, atomically replaces the user unit, reloads
  systemd, enables the unit and restarts it. Linux stop retains definition and
  enabled state.
- Flow :: Make builds before start, then invokes the build-tool task. The task
  validates configuration, prepares the platform definition and waits for every
  manager operation. Stop and restart do not build or regenerate definitions.
- Failure behaviour :: Each manager call has a 30-second deadline. Diagnostics
  are retained in contextual errors; no retry or detached fallback occurs.
- Simplicity :: No new dependency, daemon, configuration, shell command string
  or replacement transaction is introduced.

** Design decisions and verification

*** Manager lifecycle is the only service path

- Decision :: The three lifecycle targets perform only native manager operations;
  start may generate the manager-owned user definition first.
- Verification :: [[#rt-017-1][RT017.1 - Native manager restart sequence]]
  and [[#rt-017-2][RT017.2 - Systemd source-checkout lifecycle]] capture external
  calls, generated definition data and failure transitions.

** Routine details left to implementation

- Internal function names and error wording may follow established build-tool
  conventions while retaining the defined context.

** Architecture impact

*** Security impact

- Threat boundary :: The existing per-user manager boundary is unchanged.
- Data and secrets :: No document data, configuration contents or service logs
  are read or emitted.
- Access :: No privilege escalation, system service or service enablement is
  added.
- Conclusion :: Existing least-privilege ownership remains sufficient.

*** Other relevant qualities

- Portability :: All three operator targets have defined macOS and Linux behaviour.
- Reliability :: Ordered execution removes concurrent prerequisite scheduling.
